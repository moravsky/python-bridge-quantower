# Architecture

## Projects

```
proto/
  messages.proto                 -- shared wire schema (single source of truth)

PythonBridgeQuantower/
  PythonBridgeQuantower.csproj   -- Strategy, .NET 8.0, x64.
                                    References Grpc.Tools for protoc at build,
                                    Google.Protobuf at runtime, NetMQ for ZMQ.
  TradeStreamStrategy.cs         -- subscribes to NewLast and NewLevel2,
                                    serializes to protobuf, publishes on PUB.

tui/
  tape.py                        -- Python TUI, consumes from PUB or replays
                                    from JSONL capture file.
  messages_pb2.py                -- generated by grpcio-tools from
                                    proto/messages.proto. Committed for ease
                                    of use; regenerate after schema edits.

captures/                        -- JSONL capture files; one line per message
                                    wrapped as `{"topic":"...","msg":{...}}`.
specs/                           -- design specs and commit plans.
```

## Data Flow

Strategy is the publisher; TUI (and any other consumer) is a subscriber.

```
   Quantower events                  ZMQ PUB                ZMQ SUB
[NewLast, NewLevel2]  ->  Strategy  ===========>  TUI / bot consumer
                          (server)  (loopback)    (clients, N can connect)
```

Two flows:

- **Live (socket)**: strategy binds `tcp://127.0.0.1:<port>` as PUB.
  Each event (trade print, throttled DOM snapshot) is mapped to a protobuf
  message and published as a two-frame ZMQ message: `[topic, payload]`
  where `topic` is `trade` or `dom` and `payload` is `Serialize`d
  protobuf bytes. TUI connects as SUB, subscribes to the empty topic
  prefix (all messages), parses each payload based on its topic frame.
- **Replay (file)**: TUI reads a JSONL capture file written during a
  prior live session. Each line is parsed back to the original protobuf
  type via `Parse(json_body, pb)` and fed to the same typed handlers
  the live socket path uses.

## Wiring

- Strategy entry points: `OnRun` (bind PUB, subscribe to Quantower events),
  `OnStop` (unsubscribe, dispose PUB socket).
- Event subscription: `CurrentSymbol.NewLast += OnNewLast` and
  `CurrentSymbol.NewLevel2 += OnNewLevel2` in `OnRun`.
- Socket roles: **strategy is the server** (PUB, binds), **TUI is the
  client** (SUB, connects). Either side can start first; ZMQ holds the
  connection until both are up. ZMQ "slow joiner" applies: subscribers
  that connect after publication started miss the prior messages.
- DOM throttling: snapshots are emitted at most ~10/sec to keep wire
  volume bounded. Trade prints flow at native rate (subject to
  `SamplePct`).
- No reconnection logic in the strategy. If the PUB socket fails to
  bind on `OnRun` (port conflict), the strategy logs an error and stops.

## TUI internal flow

Application layer is fully typed -- protobuf objects (`TradeMessage`,
`DomMessage`, `DomLevel`) flow from the read loop to the renderers
without round-tripping through dicts:

```
_read_socket() ──┐                    ┌── _handle_trade(TradeMessage)
                 ├── parse by topic ──┤
_read_file()  ───┘                    └── _handle_dom(DomMessage)
                                                  │
                                                  v
                                          state: deque[TradeMessage]
                                                 _dom: DomMessage | None
                                                  │
                                                  v
                                          _refresh_ui() (15 fps)
                                                  │
                                                  v
                                          build_tape_table(deque[TradeMessage])
                                          build_dom_table(DomMessage)
```

The only topic demux is at the I/O boundary (`_read_socket`,
`_read_file`, `_write_capture`) -- because raw bytes don't
self-identify which protobuf type to parse. Once the right type is
chosen, everything downstream is statically typed.

## Wire protocol

Two ZMQ frames per message:

1. **Topic** (UTF-8 string, 4-5 bytes): `trade` or `dom`. Also tells
   the subscriber which protobuf message type to parse the payload as.
2. **Payload**: protobuf-encoded `TradeMessage` or `DomMessage`,
   defined in `proto/messages.proto`.

Schema (`proto/messages.proto`):

```proto
message TradeMessage {
  string symbol = 1;
  string ts = 2;
  double price = 3;
  int64  size = 4;
  string side = 5;
}

message DomLevel {
  double price = 1;
  int64  size = 2;
}

message DomMessage {
  string symbol = 1;
  string ts = 2;
  repeated DomLevel bids = 3;
  repeated DomLevel asks = 4;
}
```

### Codegen

- **C#**: `Grpc.Tools` NuGet adds a `<Protobuf>` build target to the
  csproj; `protoc` runs at build, generates types into `obj/`. The
  generated namespace is `PythonBridgeQuantower.Proto` (set via
  `option csharp_namespace` in the .proto). No gRPC server code is
  generated -- the csproj specifies `GrpcServices="None"`.
- **Python**: `grpcio-tools` provides `python -m grpc_tools.protoc`,
  which generates `tui/messages_pb2.py`. The generated file is
  committed to the repo for ease of use; users don't need to run
  codegen unless they edit the .proto file. Regenerate with:

      python -m grpc_tools.protoc -I=proto --python_out=tui proto/messages.proto

- **Version pinning**: C# `Google.Protobuf` 3.27.2 pairs with Python
  `protobuf` 5.27.2 -- same protoc generation epoch. Mismatched
  versions emit a runtime warning about gencode vs runtime version
  (harmless, but noisy). Pin both sides to the same protoc generation
  to keep things silent.

## Capture file format

Each line is a JSON object: `{"topic":"<trade|dom>","msg":{...}}`.

- The wrapper carries the topic at the storage layer because, like the
  wire, a capture file mixes message types and the reader needs to
  know which protobuf type to parse each line as.
- The `msg` value is the protobuf message serialized via
  `MessageToJson(pb, preserving_proto_field_name=True)`. Field names
  match the .proto definition.
- On replay, `Parse(json.dumps(record["msg"]), pb)` reconstructs the
  typed protobuf from the JSON body.

**Int64 typing note**: `MessageToJson` + `Parse` is used instead of
`MessageToDict` because `MessageToDict` coerces int64 fields (`size`)
to Python `str` (preserves precision in JS). That breaks the TUI's
DOM bar-width math which does `int(size / max_size * bar_width)`.
The JSON round-trip keeps int64 as Python `int`.

## Settings

Strategy `InputParameter`s exposed in Quantower UI:

| Name       | Type   | Default        | Purpose                                  |
|------------|--------|----------------|------------------------------------------|
| Symbol     | Symbol | (user picks)   | Instrument to stream                     |
| SamplePct  | int    | 100            | % of trades to emit (1-100)              |
| Port       | int    | 8765           | TCP port the PUB socket binds to         |
| DOM Levels | int    | 10             | Number of order book levels per side     |

Python CLI args: `--port` for socket mode, positional file path for
file mode, `--delay` to throttle file replay.

## Decisions

- **ZeroMQ over raw TCP**: brought multiple-subscriber support, topic
  filtering, and connection-direction flexibility (either side can
  start first) without writing a custom framing layer. NetMQ is pure
  managed C#; pyzmq has good Python ergonomics. Loopback latency is
  in the same order as raw TCP (sub-millisecond for small payloads).
- **Protobuf over JSON or MessagePack**: protobuf has IDL-driven
  codegen on both sides from a single `.proto` file. JSON and
  MessagePack would each require hand-written message classes on each
  side, with no enforced contract -- a known bug factory when the C#
  and Python definitions drift. Protobuf's field-number versioning
  also handles forward/backward compatibility correctly for future
  schema evolution. Wire size is comparable to MessagePack and
  smaller than JSON. The serialization library cost (NuGet +
  pip package) is small.
- **Strategy as PUB / TUI as SUB**: previous design had the TUI as
  TCP server. ZMQ PUB on the long-lived data source side is more
  idiomatic, supports multiple subscribers naturally, and lets the
  TUI come and go without disrupting the data flow. The trade-off is
  the "slow joiner" property -- a SUB connecting after the PUB has
  been publishing for a while will miss the early messages. For a
  live monitoring TUI this is acceptable.
- **Typed objects end to end in the TUI**: protobuf message classes
  flow from `_read_socket`/`_read_file` through `_handle_*` to
  `build_*_table` without being converted to dicts. Dicts only
  appear at the capture-file I/O boundary (where storage is JSONL).
  Earlier iterations of this refactor converted protobuf back to
  dicts immediately; that defeated the point of having a typed
  schema and was abandoned.
- **Capture format `{"topic":"...","msg":{...}}`**: the topic stays at
  the storage layer because, like the wire, raw JSON body bytes don't
  self-identify the protobuf type to parse. A flat dict without the
  topic wrapper would require pattern-matching the field set to guess
  the type. The wrapper is explicit and unambiguous.
- **Generated Python file committed**: `tui/messages_pb2.py` is
  generated by `grpcio-tools`, but it's checked in so users running
  the TUI for the first time don't need to run codegen manually. The
  trade-off is that schema edits require regenerating + recommitting
  the file -- acceptable for a project with infrequent schema churn.
- **Sampling on producer only**: consumers process everything they
  receive. The producer's `SamplePct` controls volume at the source,
  keeping the consumer code simple.
- **DOM throttle at the producer**: `NewLevel2` can fire 100+/sec on
  liquid futures. The strategy throttles snapshots to ~10/sec via a
  stopwatch check; without it the wire bandwidth would balloon
  without adding visualization value to a TUI rendering at 15 fps.

## Alternatives considered and rejected

- **gRPC** (full RPC framework, not just protobuf): would give us
  typed RPC calls for free, but `Grpc.AspNetCore` requires Kestrel,
  which needs the ASP.NET Core shared framework -- Quantower's
  bundled runtime does not include it. Plain protobuf-over-ZMQ
  delivers the same shared-schema benefit without the hosting issue.
- **MessagePack with hand-written classes both sides**: simpler to
  set up than protobuf (no codegen step) but reintroduces the
  drift-between-languages bug class that motivated moving off
  newline-JSON in the first place. Tried briefly, abandoned in favor
  of protobuf.
- **Custom YAML/JSON schema with home-grown codegen**: equivalent to
  reinventing protobuf, badly. Skipped.
